# 기획·작업: 챗봇용 주문 검수 API + 주소 재응답

작성 목적: 농가 「직접 추가」의 **파싱·검수 파이프라인**을 챗봇이 재사용할 수 있게 옮기는 작업 목록.  
특히 **주소 오류**와 **우체국 검색 다건**일 때, 사용자가 다시 답하고 **수정·선택**할 수 있어야 한다.

기준 화면: [`src/pages/farm/OrderCreate.tsx`](../src/pages/farm/OrderCreate.tsx)  
기준 저장 API: [`create-farm-orders`](backend/orders/command/create-farm-orders.md)

---

## 1. 배경 / 문제

### 1.1 검수가 화면에만 있음

「카드로 변환」 후 검수 흐름의 상당 부분이 프론트에 묶여 있다.

| 단계 | 현재 위치 | 비고 |
|------|-----------|------|
| 메시지 파싱 | 서버 `parse-order-messages` | 이미 RPC |
| 상품 매칭 | 서버 `match-farm-products` + 프론트 로컬 | 오케스트레이션은 프론트 |
| 우체국 주소 확정 | 프론트 `validateDraftAddress` | `epost-address` 호출만 서버 |
| 동·호 검증 | 프론트 `checkAddressDetail` | `juso-building` 호출만 서버 |
| 필수값·전화 형식 | 프론트 `toDraftOrder` | |
| 주소/상품 수정 UI | 프론트 다이얼로그 | 챗봇에 대응 없음 |
| 저장 | 서버 `create-farm-orders` | 이미 RPC |

챗봇이 `epost-address`만 직접 부르면 **동·호·상품·필수값** 검수가 빠지고, 화면과 판정이 어긋난다.

### 1.2 챗봇에 꼭 필요한 대화 루프

우체국이 **잘 나와도** 아래면 자동 확정하지 않고 **사용자에게 다시 물어야** 한다.

1. **우체국 결과가 여러 건** → 목록을 보여 주고 번호/버튼으로 **선택**
2. **1건이지만 원문과 불일치**(시·군·구 변경 등) → 후보를 보여 주고 **확인/선택**
3. **기본주소는 확정됐는데 동·호 문제** → 상세만 **재입력** 후 재검증  
   예: 호 없음, 동 없음, 등록 호수에 없음
4. **검색 0건 / API 실패** → 주소를 다시 받거나 다른 검색어로 재시도

화면의 `EpostAddressFixDialog`가 하는 일을, 챗봇은 **텍스트 질문 → 사용자 재응답 → 서버 재검수**로 대체한다.

---

## 2. 목표 (Must)

1. **단일 검수 오케스트레이터**를 서버에 둔다. 화면·챗봇이 같은 판정을 쓴다.
2. 챗봇이 **주소 오류** 시 사용자에게 다시 묻고, 받은 값으로 **상세/기본주소를 수정**한 뒤 재검수할 수 있다.
3. 챗봇이 **우체국 다건(또는 확인 필요 1건)** 시 후보를 내려주고, 사용자가 **하나를 선택**하면 확정·동호 재검증까지 이어진다.
4. 검수 통과한 건만 `create-farm-orders`로 저장한다. (전부 아니면 전무 규칙은 유지)
5. 우체국 성공 후에도 **동·호 검증(`juso-building`)은 항상** 돌린다.

---

## 3. 비목표 (이번 작업에서 하지 않음)

- 손님용 스토어 `create-order` 플로우 개편
- 카카오 채널/스킬 인프라 전체 구축 문서화 (연동 지점만 정의)
- 우체국·juso Open API 스펙 변경
- 입금 매칭·알림톡·송장 연동

## 4. 목표 아키텍처

```
[챗봇 / OrderCreate]
        │
        ▼
 POST /rpc/review-farm-orders     ← 신규: 파싱+매칭+주소검수 일괄
        │
        ├─ parse-order-messages (내부 호출 또는 공유 모듈)
        ├─ match-farm-products
        ├─ epost-address
        └─ juso-building (checkAddressDetail)
        │
        ▼
  status=ok | needs_address_select | needs_address_fix | needs_field_fix | ...
        │
        ▼  (사용자 재응답)
 POST /rpc/review-farm-orders     ← 같은 API에 action으로 패치/선택
   action: select_address | patch_order | recheck
        │
        ▼  (전부 ok)
 POST /rpc/create-farm-orders
```

원칙:

- **판정은 서버만.** 챗봇은 응답의 `errors` / `addressCandidates`를 읽어 말할 뿐.
- **세션 상태는 챗봇이 보관**해도 된다. 다만 재검수 시 서버에 **현재 draft 전체(또는 해당 주문)** 를 다시 넘긴다. (서버를 draft DB 저장소로 쓰지 않아도 됨 — 초기안)
- 이후 필요하면 `reviewSessionId`로 서버 임시 저장을 후속으로 추가.

## 5. API 설계 (초안)

### 5.1 `POST /rpc/review-farm-orders`

권한: `create-farm-orders`와 동일 — 관리자 또는 해당 `farm_members`.

#### A) 원문 일괄 검수

```json
{
  "farmId": "uuid",
  "text": "카톡 원문..."
}
```

#### B) draft 재검수 / 주소 선택 / 필드 패치

```json
{
  "farmId": "uuid",
  "action": "recheck" | "select_address" | "patch_order",
  "orders": [ /* 직전 응답의 orders 필드 형태 */ ],
  "targetIndex": 0,
  "selection": {
    "candidateId": "우체국 결과 id",
    "addressDetail": "103동 801호"
  },
  "patch": {
    "address": optional,
    "addressDetail": optional,
    "recipientName": optional,
    "phone": optional,
    "productId": optional,
    "productQuery": optional,
    "quantity": optional
  }
}
```

| action | 의미 |
|--------|------|
| (없음) + `text` | 파싱부터 전체 검수 |
| `recheck` | 전달된 orders를 다시 주소·상품·필수값 검수 |
| `select_address` | `targetIndex` 주문에 우체국 후보 적용 → 동·호 재검증 |
| `patch_order` | 필드 수정 후 해당 주문(또는 전체) 재검수 |

### 5.2 응답 형태

```json
{
  "orders": [
    {
      "index": 1,
      "status": "ok" | "needs_address_select" | "needs_address_fix" | "needs_field_fix" | "needs_product_select",
      "fields": {
        "recipientName": "",
        "phone": "",
        "zonecode": "",
        "address": "",
        "addressDetail": "",
        "productId": null,
        "productQuery": "",
        "quantity": 1,
        "senderName": "",
        "senderPhone": "",
        "depositorName": "",
        "memo": ""
      },
      "errors": [
        {
          "field": "address" | "product" | "phone" | "recipientName" | "...",
          "code": "MULTI_CANDIDATES" | "DISTRICT_MISMATCH" | "NOT_FOUND" | "MISSING_HO" | "MISSING_DONG" | "INVALID_HO" | "UNMATCHED_PRODUCT" | "REQUIRED" | "INVALID_PHONE" | "...",
          "message": "사람/챗봇이 그대로 읽어도 되는 한글 안내"
        }
      ],
      "addressCandidates": [
        {
          "id": "",
          "zipNo": "",
          "roadAddress": "",
          "jibunAddress": ""
        }
      ],
      "addressSearchQuery": "마지막으로 쓴 우체국 검색어",
      "productCandidates": [
        { "id": "", "name": "", "unit": "", "price": 0 }
      ]
    }
  ],
  "summary": {
    "total": 1,
    "ready": 0,
    "needsFix": 1
  }
}
```

### 5.3 `status` / `code` ↔ 챗봇 행동

| status / code | 챗봇이 할 일 | 사용자 재응답 예 | 다음 action |
|---------------|--------------|------------------|-------------|
| `needs_address_select` + `MULTI_CANDIDATES` | 후보 1,2,3… 번호로 제시 | `2` 또는 도로명 일부 | `select_address` |
| `needs_address_select` + `DISTRICT_MISMATCH` | 원문 구 vs 우체국 구 안내 후 후보 확인 | `맞아요` / `1` | `select_address` |
| `needs_address_fix` + `MISSING_HO` 등 | 상세주소만 다시 요청 | `103동 801호` | `patch_order` (`addressDetail`) |
| `needs_address_fix` + `NOT_FOUND` | 주소 전체 다시 요청 | 새 도로명 주소 | `patch_order` (`address`±detail) |
| `needs_product_select` | 후보 상품 제시 | `1` 또는 상품명 | `patch_order` (`productId`) |
| `needs_field_fix` | 해당 필드만 재질문 | 이름/전화 등 | `patch_order` |
| `ok` | 다음 미해결 주문으로 넘어가거나 저장 확인 | `등록` | `create-farm-orders` |

**중요:** `addressCandidates`가 있으면 챗봇은 **임의로 1번을 고르지 않는다.** 반드시 사용자 선택을 받는다. (화면이 다건에서 자동 확정하지 않는 것과 동일)

**중요:** 기본주소가 이미 확정된 뒤 동·호만 틀리면 `addressCandidates`에 확정 후보 1건을 남겨, 상세만 고쳐도 같은 도로명으로 재검증할 수 있게 한다. (현재 `OrderCreate` 주석: “기본주소는 확정됐고 동·호만 확인”)

## 6. 챗봇 대화 시나리오 (필수)

### 6.1 우체국 다건

1. 사용자: 주문 메시지 붙여넣기  
2. 봇: `review-farm-orders` (`text`)  
3. 응답: `needs_address_select`, candidates 3건  
4. 봇:  
   `주소가 여러 건 검색됩니다. 번호를 골라 주세요.`  
   `1) [07500] 서울 강서구 …`  
   `2) …`  
5. 사용자: `1`  
6. 봇: `select_address` + `candidateId` (+ 있으면 기존 detail)  
7. 동·호까지 ok면 다음 단계, 아니면 6.2로

### 6.2 동·호 오류 (우체국은 이미 성공)

1. 응답: `needs_address_fix`, code `MISSING_HO`, message `호수가 빠졌습니다`  
2. 봇: `공동주택으로 보여요. 동·호수를 알려 주세요. 예: 103동 801호`  
3. 사용자: `103동 801호`  
4. 봇: `patch_order` `{ "addressDetail": "103동 801호" }`  
5. 서버: 기존 확정 도로명 + 새 상세로 `checkAddressDetail`  
6. 통과 시 `status=ok`

### 6.3 선택 후 상세까지 한 번에

다건 선택 시 상세가 비어 있으면:

1. 선택 직후 바로 `MISSING_HO`가 날 수 있음  
2. 봇은 이어서 상세만 묻고 `patch_order`  
3. 또는 챗봇 UX로 “주소 번호 + 동호”를 한 메시지에 받아 `select_address`의 `addressDetail`에 같이 넣어도 됨

### 6.4 저장

`summary.needsFix === 0` 일 때만:

- 봇: `N건 모두 확인됐습니다. 등록할까요?`  
- 사용자 확인 후 `create-farm-orders`에 `fields`를 기존 요청 스키마로 변환해 전송

## 10. 구현 순서 (추천)

1. **공유 검수 모듈** 서버에 추가 (주소 + 동호 + 필드 + 상품 오케스트레이션)  
2. **`review-farm-orders` RPC** — `text` 일괄 / `select_address` / `patch_order` / `recheck`  
3. **단위·수동 테스트**  
   - 다건 주소 → 선택 → ok  
   - 유일 주소 + 호 누락 → detail 패치 → ok  
   - 구 이름 mismatch → 선택 후 ok  
   - 상품 미매칭 → productId 패치 → ok  
4. **챗봇 대화 루프** 연결 (6절 시나리오)  
5. (권장) **OrderCreate**를 동일 API로 전환  
6. 문서·README 링크 정리

## 11. 수락 기준 (Acceptance)

1. 챗봇만으로(웹 OrderCreate 없이) 카톡 원문 → 검수 → **다건 주소 선택** → 등록이 가능하다.  
2. 챗봇만으로 우체국 1건 확정 후 **호수 누락**을 사용자 재응답으로 고친 뒤 등록이 가능하다.  
3. 동일 원문에 대해 웹 「카드로 변환」과 챗봇 `review`의 `errors[].code`가 같다. (5단계 리팩터 후)  
4. `needsFix > 0` 인 채 `create-farm-orders`를 부르면 챗봇이 막고, 서버도 불완전한 주소/상품을 거절한다.  
5. 우체국 다건일 때 서버·챗봇 いずれも **사용자 선택 없이 1번 후보를 넣지 않는다.**

## 13. 열린 결정 (구현 전 합의)
